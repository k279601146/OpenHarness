# Workflow Composer

## 目标

把用户的复杂目标转成可执行交付流，串联附件、项目上下文、已授权连接器、内置/已安装技能和必要的 Agent 能力，尽可能直接完成第一版交付物或任务目标。

这是执行型元技能：负责拆解目标、选择能力、发现缺口、安装确认、串联上游/下游产物、复核结果和收口交付；不替代每个领域技能的具体工作，也不把用户留在建议层。

核心目标不是输出“工作流说明”，而是把用户的真实目标推进到一个合法终态：已交付、等待确认、明确受阻，或用户明确要求的规划态。

## 默认行为

- 默认继续执行到可用交付，除非信息不足以开始、需要授权/付费/外部写入确认，或用户明确要求只分析/只讨论/先不修改。
- “方案、建议、路线图、下一步清单”默认只是中间产物；除非用户明确只要这些，否则不能作为动作型目标的最终完成。
- 用户选择了本技能但任务实际很小，也要直接完成那个小任务；不要解释“无需编排”后停止。
- 先执行当前安全边界内可以执行的步骤，再汇总已完成内容、关键假设、缺口和需要确认的动作。
- 每个中间产物都要命名，并明确传给哪些后续步骤使用。
- 技能名、市场搜索、插件权限和安装细节默认留在幕后；只有需要用户确认、授权、安装或排查时才展示。
- 如果一个现有技能明显能直接完成任务，交给该技能完成，不启动完整编排。

## 触发边界

只有当请求满足以下任一条件时，才使用完整编排：

- 至少 3 类能力或阶段要串联，例如读取资料、清洗数据、生成 PPTX、写同步文案、创建提醒、复核结果。
- 至少 2 个不同交付物要共同完成，例如文档、表格、PPTX、图片、网页、消息草稿、日程、任务清单。
- 需要外部系统或连接器参与，例如飞书、腾讯文档、邮箱、CRM、Webhook、日历、知识库、工单系统。
- 用户描述的是工作/生活 outcome，而不是明确的单个工具操作。
- 需要发现、安装或启用额外能力才能完成目标。

不要使用完整编排：

- 一个现有技能明显能直接完成任务，例如只读 PDF、只生成 PPTX、只分析表格、只写一篇通知。
- 用户只是要求快速润色、翻译、少量总结、普通问答或简单头脑风暴。
- 用户已经手动选择技能，并且这些技能足够完成任务。
- 当前最合理动作只是问一个澄清问题，然后执行一个小任务。

不确定时采用轻量模式：用 2-4 个内部步骤继续执行，不主动搜索市场；执行中发现能力缺口再升级。

## 执行型 SOP

### 1. 判定模式

先判断用户是否要求规划态还是交付态：

- 规划态：用户明确说“先讨论、只分析、只给方案、先不要执行、不要修改、先评估”。此时可以停在规划层。
- 交付态：用户表达的是“做成、生成、制作、发布、发送、上传、创建、整理成、交付、完成、落地、执行”等结果目标。此时必须推进到合法终态，不能只给建议。

不确定时按交付态处理，除非继续执行会越过确认边界。

### 2. 建立目标契约

内部识别并转成完成标准：

- 核心结果
- 需要交付的产物
- 输入来源，例如附件、项目上下文、历史产物、连接器、网页、表格、会议记录
- 受众、语言、风格、截止时间、平台、格式等约束
- 是否简单到不需要工作流编排
- 用户是否明确要求只规划、不修改或先讨论

把目标写成一句内部完成标准：本轮要交付什么，或必须向用户确认什么，或为什么无法继续。不要把“给出一个流程”当成默认完成标准。

### 3. 拆解交付步骤

把目标拆成 3-7 个交付步骤。每步内部记录：

- 这一步完成什么
- 使用哪些输入
- 产出什么可复用中间件或最终交付物
- 依赖哪些前置步骤
- 是否可以跳过或降级

能并行时使用 DAG 思路，不强行排成线性清单。

### 4. 选择或发现能力

对每个步骤：

- 先检查用户提供的附件、当前任务上下文、历史产物和已授权连接器。
- 再检查用户已选择的技能。
- 再检查 bundled/official 和已安装技能。
- 本地能力不够时，用 `skillhub_search_capabilities` 搜索 SkillHub 候选；需要更细的检索策略时加载 `find-skill`。
- 按能力和场景检索，不只按产品名检索。例如搜「social media travel guide copywriting」，而不是只搜「小红书」。

选择最小可行能力集合。不要因为市场上有技能就安装；必须先证明本地能力不够。

### 5. 执行安全步骤

先完成不需要额外确认的动作，例如读取资料、抓取公开网页、整理附件、生成第一版脚本/文档/表格/清单/草稿/执行包、调用已授权的只读连接器、产出可复用中间件。

执行时遵守：

- 能根据现有信息做出合理假设时，先做第一版，不要把可假设的问题变成阻塞提问。
- 如果自然需要文件、媒体、表格、PPTX、压缩包或可下载结果，优先生成真实产物并交付，而不是只把内容贴在聊天里。
- 如果只能在聊天里交付，也必须是可直接使用的完整内容，例如可发布文案、可拍摄脚本、可发送邮件、可执行检查表；不能只是建议。
- 上游产物必须明确传给下游步骤，例如“网站卖点摘要”传给“短视频脚本”和“发布文案”。

### 6. 确认边界

安装任何 SkillHub/市场能力前：

1. 调用 `skillhub_prepare_install` 获取 `confirmation_id`、安装类型和风险。
2. 用 `ask_user_question` 简短说明需要补充的能力、来源、风险，并询问是否安装。
3. 用户确认后调用 `skillhub_install_confirmed`。
4. 安装成功后，继续执行原工作流，不把用户留在安装步骤。

以下情况也必须确认：

- 使用 API key、外部账号、外部服务或付费能力。
- 外部写入、上传、发布、发送、删除、部署、提交、创建日程、创建任务等会改变外部系统的动作。
- 工作流存在影响结果的关键歧义。

需要确认时，不要用“如果你愿意我可以继续”收尾；使用 `ask_user_question` 让任务进入等待确认状态。确认问题必须说明要执行的动作、会影响什么、默认推荐选项是什么。

### 7. 完成前自检

最终回复前逐项检查：

- 我是否只是给了方案、建议或下一步？
- 用户真实动词是否已经推进，例如制作、生成、整理、发布、发送、上传、创建或交付？
- 是否至少交付了一个可直接使用的产物，或已经请求必要确认，或明确说明已尝试但受阻？
- 如果涉及外部写入、发布、发送、上传、付费、授权或账号连接，我是否已经请求确认，而不是假装完成？
- 后续可选动作是否只是补充，而不是把核心工作推给用户？

如果答案显示仍停在建议层，继续执行；不能直接结束。

## 合法终态

只能在以下状态收口：

- 已交付：完成了用户目标的第一版可用产物，例如文件、媒体、表格、PPTX、发布包、同步草稿、行动清单、可运行工具、知识库草稿或可直接复制使用的完整内容。产物必须对应用户的主要动词。
- 等待确认：继续会触发授权、付费、外部写入、上传、发布、发送、删除、部署、创建日程或安装能力，已经用 `ask_user_question` 请求确认。
- 明确受阻：已经尝试执行，但资料、权限、工具、连接器或能力缺失；说明尝试过什么、卡在哪里、用户提供什么后可以继续。
- 规划态完成：用户明确要求只分析、只讨论、只规划或先不执行。

不要把“下一步建议”“推荐你可以做”“如果你愿意我可以继续”作为交付态任务的主要结尾。

## 交付判定

按用户的主要动词判定什么才算交付：

- 用户说整理、总结、提炼、撰写、生成文案、做清单：完整可复制内容可以算已交付。
- 用户说制作文件、做表格、做 PPTX、打包资料：聊天正文通常不够，应生成文件或明确说明为什么只能给草稿。
- 用户说生成图片、生成视频、制作视频、配音、剪辑：脚本、分镜和素材清单只是预制作；必须继续到媒体生成结果，或在需要付费/授权/外部能力时进入等待确认。
- 用户说发布、发送、上传、创建、写入、同步、部署：本地草稿不是完成；必须进入外部动作确认，或在确认后执行。
- 用户说完整推进、端到端、工作流、一整套：至少交付两个互相衔接的产物，或一个产物加一个必要确认。

最终回复按状态收口：先说“已交付”“等待确认”“受阻”或“按你的要求先完成规划”，再列已完成产物。可选后续动作只能放在已交付或等待确认之后，不能代替核心交付。

## 场景 SOP

- 只有进入某个步骤时，才加载对应技能。
- 明确把上游产物传给下游步骤。
- 给每一步产物命名，方便复用和回溯。
- 只要不会越过授权或外部写入边界，就用现有资料先交付第一版。
- 如果技能或连接器失败，先尝试保守替代方案；仍失败再回到用户。
- 结束时汇总已交付产物、关键假设、未解决缺口和需要用户确认的后续动作。

### 内容制作与发布

当用户目标是“制作并发布内容、宣传产品、投放社媒、发送营销材料”等：

1. 先读取或整理可用资料，提炼受众、卖点、限制和平台语境。
2. 直接产出第一版可用内容包，例如脚本、分镜、字幕、标题、正文、标签、素材清单、拍摄表、复核清单。
3. 如果用户主要目标包含“制作视频、生成视频、发布视频、上传视频”，内容包只是预制作结果；继续推进到媒体生成或发布确认，不能把内容包当作最终完成。
4. 如果需要调用付费媒体生成、外部账号、上传或发布，先用 `ask_user_question` 请求确认；确认后继续原工作流。
5. 没有发布授权时，交付发布前内容包并进入授权确认，不能宣称已经发布。

### 文档、表格、PPTX 和知识库

当目标包含文档、表格、PPTX、知识库或多产物沉淀：

1. 先读取资料并形成可追溯摘要。
2. 生成用户可以直接使用或继续编辑的产物。
3. 需要写入外部协作系统、上传文件或发送通知时先确认。
4. 最后列出已交付文件/草稿、未验证事实和建议复核点。

### 连接器和外部系统

当目标需要飞书、企业微信、邮箱、CRM、日历、Webhook、知识库或工单系统：

1. 已授权的只读查询可以直接执行。
2. 写入、发送、创建、更新、删除、发布、关闭订单或改变外部状态前必须确认。
3. 如果连接器未授权，交付本地草稿或执行包，并请求授权或替代路径。

## 示例

用户说：「帮我把这次产品上线做成完整推进流，材料有 PRD、排期表、会议纪要和客户反馈，还要输出发布 PPT、检查表、官网文案和团队同步。」

应先整理资料，再串联文档读取、表格整理、PPTX、内部沟通和复核能力，直接产出第一版发布 PPTX 内容、上线检查表、官网/社媒/邮件文案和团队同步草稿。若需要发送到外部系统、上传文件、创建日程或安装新能力，先向用户确认，确认后继续完成原任务。

用户说：「我想在短视频平台发布视频，宣传我的网站，吸引用户来。」

应先读取网站公开资料并提炼卖点，再交付首版短视频内容包，例如脚本、分镜、字幕、标题、发布文案、标签、素材清单和复核清单。如果要调用视频生成、上传视频或发布到外部平台，先请求确认；确认后继续制作或发布。不能只输出“建议你这样拍”后结束。
