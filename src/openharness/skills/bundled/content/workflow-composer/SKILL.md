# Workflow Composer

## 目标

把用户的场景需求转成透明、可确认、可执行的工作流方案，同时把技能机制隐藏在幕后。用户应该看到目标、步骤、输入、产物、权限和风险，而不是被迫理解技能名、市场安装、插件权限或技能组合逻辑。

这是一个元技能：它负责规划、筛选、组合和协调其他技能，本身不替代每个领域技能。

## 触发边界

只有当请求至少满足以下两项时，才使用完整工作流编排：

- 目标需要多个不同产物，例如文档、表格、图片、网页、PPT、日程、发布文案。
- 用户描述的是生活/工作场景，而不是一个明确的工具操作。
- 任务自然包含调研、创作、转换、审校、发布、自动化等多个阶段。
- 任务可能需要从 SkillHub、能力市场或已安装技能中发现额外能力。
- 步骤之间有依赖关系，例如先调研再写作，先清洗数据再做图表。
- 用户明确说要工作流、方案、pipeline、端到端处理、一整套解决方案。

不要使用完整编排：

- 一个现有技能明显能直接完成任务。
- 用户只是要求快速润色、翻译、少量总结、普通问答或简单头脑风暴。
- 用户已经手动选择技能，并且这些技能足够完成任务。
- 当前最合理动作只是问一个澄清问题，然后执行一个小任务。

如果不确定，先采用轻量模式：给出简短步骤并继续执行，不主动做市场检索，除非任务明显需要额外能力。

## 产品原则

- 技能对用户隐藏，方案对用户透明。
- 尊重用户显式选择。用户手动选过的技能优先作为候选。
- 优先使用 official/bundled 内置技能，其次已安装用户技能，再考虑 SkillHub/市场技能。
- 不随机组装技能。选择能完成目标的最小技能集合。
- 可靠的通用技能优先于名称漂亮但质量未知的小众技能。
- 安装市场技能、启用插件、使用凭据、访问外部服务或执行不可逆动作前，必须先让用户确认。
- 缺失能力要作为计划缺口说明，不要静默假设。

## 编排流程

### 1. 判断是否值得编排

先在内部用一句话复述用户目标，并识别：

- 核心结果
- 需要交付的产物
- 受众、语言、风格、截止时间、平台、素材来源等约束
- 是否简单到不需要工作流编排

如果是简单任务，停止使用本技能的完整流程，直接回答或调用单个合适技能。

### 2. 拆解能力步骤

把目标拆成 3-7 个能力步骤。每个步骤应包含：

- `intent`：这一步用用户能理解的话完成什么
- `input`：需要什么输入
- `output`：产出什么
- `depends_on`：依赖哪些前置步骤
- `optional`：是否可以跳过

能并行时使用 DAG 思路，不要强行排成线性清单。

### 3. 发现候选技能

对每个能力步骤：

- 先检查用户已选择的技能。
- 再检查已安装技能和 bundled/official 内置技能。
- 本地能力不够时，使用可用的技能发现能力，例如 `find-skill`、`find-skills`、marketplace cache search 或 SaaS skill-market catalog。
- 按能力和场景检索，不只按产品名检索。例如检索「social media travel guide copywriting」，而不是只搜「小红书」。

需要安装市场技能时，优先使用 SaaS 能力市场或现有 marketplace API/工具链，因为它们负责 SkillHub 下载、Zip 校验、插件识别、权限确认和用户私有目录安装。只有安装已知 bundled/internal 技能且当前运行时提供该路径时，才考虑使用 `install_skill`。

### 4. 保守排序候选

在离线“技能可信画像”尚未建立前，用以下临时质量信号排序：

- official/bundled 且能力足够时优先。
- 已安装技能和新安装技能质量接近时，优先已安装。
- 下载量、收藏数、星标数、安装数、更新时间和描述清晰度越好，可信度越高。
- `SKILL.md` 清楚、示例具体、输入输出明确、不需要 API key，会提高可信度。
- 安全状态未知、描述缺失、同名但模糊、需要 API key、需要插件权限，会降低可信度。

处理同名或重复技能时，不按名字判断，按能力匹配判断：输入、输出、场景、示例和当前步骤是否一致。

拒绝以下候选：

- 不能清楚解决该步骤。
- 要求与该步骤无关的权限。
- 和已选技能重复但没有新增价值。
- 为了很小收益引入明显安装或配置成本。

### 5. 生成内部工作流对象

内部推理可以使用紧凑结构：

```json
{
  "title": "用户可理解的工作流标题",
  "goal": "具体目标",
  "steps": [
    {
      "id": "research",
      "intent": "整理目的地信息和路线选项",
      "input": "目的地、天数、预算和偏好",
      "output": "调研笔记和路线候选",
      "selected_capability": "research skill or built-in tools",
      "depends_on": []
    }
  ],
  "install_required": [],
  "questions": [],
  "risks": []
}
```

技能名默认留在内部；只有需要用户确认安装、授权或排查时才展示。

### 6. 给用户展示透明方案

向用户展示：

- 简短标题和最终结果。
- 3-7 个用户语言的步骤。
- 预计交付物。
- 需要用户补充的输入或决策。
- 需要安装或授权的额外能力。

不要把原始技能列表作为主要输出。应该说「我需要补充一个旅行路线规划能力」，而不是直接说「我要安装 `some-slug`」，除非用户正在确认安装。

### 7. 安装或执行前确认

以下情况必须确认：

- 安装 SkillHub/市场技能或插件。
- 使用需要 API key、外部服务、账号访问、联网调用或付费模型的能力。
- 工作流存在明显歧义。

如果不需要新安装或敏感动作，可以简短说明方案后直接继续执行。

### 8. 执行和复盘

执行时：

- 只有进入某个步骤时，才加载对应技能。
- 明确把上游产物传给下游步骤。
- 给每一步产物命名，方便复用和回溯。
- 如果技能失败，先尝试一个保守替代方案；仍失败再回到用户。
- 结束时汇总交付物、未解决缺口、可选后续动作。

在当前对话中记录实践反馈：哪些能力有效、哪些失败、用户接受了什么。这些反馈应影响同一线程后续的技能选择。

## 示例

用户说：「我想做一个小红书旅行攻略，包含路线规划、预算表、封面图、正文排版和发布文案。」

应使用本技能，因为它需要多个产物和多个能力步骤。

可生成方案：

1. 补齐目的地、天数、预算档位和风格偏好。
2. 整理目的地资料和路线选项。
3. 生成 3 天/5 天行程方案。
4. 生成预算表。
5. 生成封面图概念或图片。
6. 输出小红书标题、正文、标签和发布排版。
7. 统一检查路线、预算、图片和文案是否一致。

如果需要市场技能，先按 official/installed 优先，再参考下载量、收藏数、星标数、更新时间和描述匹配度排序，并在安装前请求用户确认。
